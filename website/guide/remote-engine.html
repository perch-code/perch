Remote hosts (SSH)

Keep checkouts, language servers, and agent runs on an SSH host while driving native Perch windows locally.

Setting up a host

The host is Linux or a Mac, on x86_64 or arm64, and reachable with ssh <host>. The app brings its own perchd and starts it there (see The app's own engine), so nothing of Perch's has to be put on it first. On it:

  1. On Linux, install bubblewrap and socat (apt install bubblewrap socat, or your distribution's), which Claude Code's sandbox needs there, or turn the sandbox off (see Without Claude Code's sandbox).
  2. Sign in to what the engine uses, as the user it runs as: gh auth login (or token in its config.toml), and each agent CLI you run, claude, codex, agy or opencode. Nothing is copied from the Mac.

Open Settings > Environment in the window you want to change. Enter the SSH host and select Connect. That window opens the host’s repositories and agent runs. Use local environment brings it back to this machine. Switching closes the current item. Other windows keep their environment and open items.

Your login at the foot of the sidebar is the one signed in to GitHub in the window’s environment, with the environment’s name under it. Click it for a menu of environments: this machine, each host a window has connected to and any host a window has open, with the window’s own checked. Choosing one switches the window to it. Connect to SSH host… opens Settings > Environment for a new host. The × on a host no window has open takes it out of the menu. The hosts connected to are kept in hosts.json in this machine’s Perch home.

Perch reopens the windows from your previous session, including each window’s environment, size and open item. A remote window reopens its item when its host connects. Closing one window removes it from the session. Closing the last window keeps it for the next launch.

New Window inherits the environment of the window in front. On a first launch with no saved windows, Perch uses the existing [remote] host in the local config if one is set, or opens locally.

The host is named as ssh is given it: a name from ~/.ssh/config, or user@host. A port goes after it, chris@devbox:2222, or the whole can be a URL, ssh://chris@devbox:2222; ssh itself takes a port only as an option, so Perch passes it as one, to the connection, the install and Open in Terminal alike, and Zed's link carries it. VS Code's does not: with a port, or an IPv6 address, Open in Editor needs Zed, or a name for the host in ~/.ssh/config. An IPv6 address with a port is in brackets, [fe80::1]:2222. ssh must connect with no question asked, a password or a host key to accept: Perch runs it in batch mode.

A Mac that is a host is kept from idle sleep for as long as its engine runs (perchd holds caffeinate -i on itself), since its work is done with nobody at it. Shutting a laptop's lid still sleeps it.

Repositories are added from the app (see Adding a repository on a host); nothing has to be cloned or written on the host first.

Adding a repository on a host

Add repository… would offer the Mac's folders, which the host has none of. With a host, wherever it is asked for, it opens Settings > Repositories, where the last row is a box and an Add button in place of the folder chooser. Type one of:

  • A repository on github.com, as owner/name or its URL. The engine clones it on the host, with its own GitHub token, to <name> in the folder the Clone into row beside it names (clone_root in the host's config.toml, such as "~/Code"), or in the home directory there with none, and adds it. A folder of that name that is already a clone of it is used as it is; any other is left alone and named. The token is given to that one git clone and is not written into the clone, whose later fetches and pushes use the host's own git credentials, as gh auth login sets them up.
  • A path on the host, starting with / or ~/: a clone already there.

Enter or Add sends it; clicking away sends nothing. The app says a named repository is being added, and that it was added, since a clone can take a while. What was typed stays in the box until then, so a refusal, which the popup explains, can be put right. A repository on a GitHub Enterprise host is cloned by hand and added by its path.

Connecting

Windows using the same SSH host share a connection. Perch starts the local engine when a window first uses the local environment. To reach a remote environment, Perch runs

ssh -T -o BatchMode=yes -o ConnectTimeout=10 -o ServerAliveInterval=15 \
    -o ServerAliveCountMax=3 -o ForwardAgent=no -o ForwardX11=no \
    -o ClearAllForwardings=yes -- <host> <command>

and talks to the engine on the host over ssh's stdin and stdout. The command runs ~/.perch/bin/perchd-<build> bridge (see The app's own engine), or [remote] command when the Mac's config.toml sets one for its default host, in your login shell either way. ssh's own config, keys and agent apply to logging in, but nothing is forwarded, whatever the config says: not the agent, not X11, no ports. Nothing is asked either, as there is no terminal: connect once with ssh <host> in a terminal to accept the host's key, and keep a key with a passphrase in the agent or the macOS keychain. The command is run in your login shell on the host, bash, zsh or fish, so the engine has the PATH your profile sets and finds git, gh and the agents where you do. What ssh says on stderr goes to the log. PERCH_SSH in the app's environment names another ssh program to run, everywhere the app runs one.

The host's engine keeps its items, runs and checkouts going with the app closed. Paths the app shows are the host's, and ~ in them is the host's home. What would open a path on the Mac reaches the host instead:

  • Open in Terminal opens Terminal with ssh -t -- <host> 'cd -- <path> && exec $SHELL -l'.
  • Reveal in Finder becomes Open in Editor: Zed, as zed ssh://<host>/<path>, when its zed command or the app is installed, else VS Code, as code --remote ssh-remote+<host> <path>. When neither can be run, the window says so.
  • Only a full path is opened. Open in Terminal refuses a path with a quote, a backslash, a ! or a control character, since the Mac's login shell reads the line and fish or csh quote differently from sh.
  • Copy Path copies the host's path.

While the host can't be reached, a strip along the foot of each window using it says so: "Disconnected from <host>. Reconnecting…", or "Can't connect to <host>" before the first connection, with ssh's last line under it (an unknown host, a refused key) and a Reconnect button. Perch tries again after a second, then two, doubling to every 30 seconds; Reconnect gives up a try under way and tries now. A try the engine has not answered in 30 seconds is given up. A connection that is lost within a minute of being made does not start the waits again from a second, so an engine that fails as it starts is not restarted every second. The windows keep what they showed. A command sent meanwhile, a click or a comment, is not done and not kept for later: the window says "Not connected to <host>, so that wasn't done." What a window asked for while the first try was under way is sent if it connects, and said not done if it fails. A window losing or gaining the keyboard, and a comment's picture, are not refused: the engine hears which window has the keyboard once connected, and pictures that never came are asked for again. When the connection is back, each window catches up on everything (the rows, the inbox, the runs, the settings) and reads its item again, or opens the one it was opening. An item showing is read again under what shows, so text typed into its composer or review is kept. Opening a notification, the Open box, a search result or Start work while disconnected puts "The connection to <host> was lost before this opened. Try it again." on the progress card. Losing the connection after asking, before the engine answers, says instead that it may have been done and to look for it in the list before trying again. Neither is done again by itself, since Start work done twice makes two branches.

When the app and the engine speak different versions of the wire, the engine refuses the app and Perch stops trying until you press Reconnect. With the app's own perchd, the strip offers to restart the engine (see When the engine is another build); with [remote] command, it says which one to update.

In a remote window, repositories, agents and GitHub settings belong to the host. Appearance, display and keyboard shortcuts come from the app’s local configuration. General > Configuration files shows where each file lives. If a file cannot be read, Perch keeps its last settings and disables edits to that file. You can still switch the window’s environment.

What runs where

The host runs the engine: the GitHub client and its token, perch.db, the checkouts and worktrees, the language servers, the agents and their approvals, and its config.toml's settings. The Mac runs the windows, draws the code and pictures, and keeps its own [ui], [display], [keybindings] and [remote], and where its windows were left, in its own Perch home.

With the Mac closed or asleep, the engine goes on for as long as it has work: runs started from the Mac keep going, queued ones start as others finish, and meanwhile the inbox is polled and checks are watched. Once it has had no client connected and no run queued or under way for 15 minutes, the engine the app started stops, as SIGTERM stops it, and nothing of Perch's runs on the host. The app starts it again when it next connects: reopening the app, or waking the Mac, catches every window up with what happened, from GitHub and from what the engine recorded. A run counts until it has ended, one waiting on an answer included, and so does a repository still being cloned for Add repository. An engine started by hand with perchd serve stays until it is stopped. A Work run that asks something while no Mac is connected waits for an answer, up to eight hours by default; the card is there when a window connects, and is answered from there as on the Mac. Stopping perchd interrupts its runs, as quitting the app does.

What the app checks

The engine on a host looks at the host as it starts, again whenever its config.toml changes or it takes up a new GitHub token, and tells every connected app what it found. Settings > Environment > Host setup shows required checks that need attention, with instructions you can copy. Show details lists passed checks and optional tools. A setup issue also appears at the foot of each window using that host, with an Open Settings button. perch --connect prints the same list. It checks:

  • GitHub token (required): one is found, as the engine finds it: GITHUB_TOKEN, GH_TOKEN, gh auth token, token in its config.toml, then the two variables as the login shell there exports them. Only whether there is one, and where it came from, is said; the token never leaves the host. Fix: gh auth login.
  • git (required): git --version runs. Fix: the install command for the host's package manager (apt-get, dnf, yum, pacman, zypper or apk).
  • Repositories (required): at least one [[repo]] has a root that is a directory on the host. Roots that are not there are named. For a github.com repository the fix is the git clone that puts it there. While it fails, its row has an Add repository… button, which goes to Settings > Repositories.
  • Claude Code, Codex, agy (Gemini), OpenCode: each agent CLI as the engine's agent discovery found it, with its path and version. None is required while another is installed; with none at all, Claude Code is. Fixes: curl -fsSL https://claude.ai/install.sh | bash and npm install -g @openai/codex; agy points at its documentation.
  • bubblewrap and socat (required, on Linux with Claude Code): both on PATH, for Claude Code's sandbox. Fix: the package manager's install. With the sandbox turned off in config, it reads Off, on any platform, and never needs setup.
  • logind (required, on Linux): loginctl show-session says logind does not kill the user's processes at logout. Fix: a drop-in that adds the user to KillExcludeUsers, then a restart of systemd-logind. With no loginctl, or no logind to ask, as in a container, there is no check.

Each command runs with a timeout of ten seconds, beside the engine's work, and one that runs out counts as missing. The app's own engine, on the Mac, checks nothing.

Limits

  • With [remote] command set, nothing updates perchd on the host. When the app is updated and the wire changes, the strip says to update the engine; install the new release's perchd and restart it.
  • Windows hosts are not supported.

For perchd CLI flags, socket locking, and how the app uploads and replaces remote engine binaries, see perchd and engine lifecycle.
