Authentication

How Perch finds a GitHub token from a desktop launch, and what permissions reviews, merges, and issues need.

On this page
  • Credential lookup order
  • Desktop launches and login shells
  • Required GitHub permissions

Credential lookup order

Perch calls GitHub's API directly. It resolves credentials in this order:

  1. GITHUB_TOKEN
  2. GH_TOKEN
  3. gh auth token
  4. token in ~/.perch/config.toml
  5. GITHUB_TOKEN, then GH_TOKEN, as your login shell exports them

Desktop launches and login shells

Using gh auth login is the simplest setup for the desktop app because a GUI launch does not normally inherit shell environment variables: opened from Finder or the Dock, Perch never sees an export in ~/.zprofile or ~/.zshrc. The last step is for that. With no token from the first four, Perch starts $SHELL as a terminal does, as a login and interactive shell, and reads the two variables from the environment it ends up with. It does this once, the first time it finds no token, and gives the shell five seconds; so an export added while Perch runs is found the next time Perch starts, while a gh auth login or a token in the config is found on the next poll.

Required GitHub permissions

The credential must be allowed to read and update notifications and to read the repositories you open. Merging a pull request also requires Contents: write permission on its repository, as does pushing a branch from Perch's own clone; opening a pull request requires Pull requests: write. Commenting on, approving, or requesting changes on a pull request requires Pull requests: write permission, as do resolving a thread and reacting to a pull request or anything said on it; reacting on an issue requires Issues: write, as do Close as issue and closing an issue.
