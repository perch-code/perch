Field guide / Start work

Worktrees

Cut a branch into its own worktree from a prompt, an issue, or any pull request without disturbing your main clone.

On this page
  • New worktree composer
  • Start work from an item
  • Keeping work safe

New worktree composer

+ at the top of the sidebar, or Cmd-N from anywhere, opens the new-work view, titled New worktree in the bar: a box for what the work is, and under it three chips.

  • Repository: the [[repo]] entries in the file's order, a local one marked (local). It opens on the open item's repository, else the last one picked. Add repository… picks a folder and appends a [[repo]] naming its repository to config.toml, without rewriting the file; Perch takes it up at once.
  • Base: the branch to start from. For a repository with a root, the root's local branches and its remote's, with no network; for a GitHub repository without one, GitHub's. It opens on the repository's base branch.
  • New branch: the name of the branch to cut, filled in from the message (branch_prefix, then its first five words) until you type in it. A name you typed that is taken is an error; one Perch filled in gets -2.

With a message, Start makes the worktree, opens it named for the message's first line, and sends the message to the agent picked beside it as the item's first Work run. Without one, Create worktree makes the worktree alone. Escape, Cmd-[, or the bar's X leaves the view and keeps what was typed until Perch quits.

Worktrees go under ~/.perch/worktrees/ by default, named for the repository and the branch. To put new worktrees elsewhere, set worktrees_dir.

A repository with a root is cut in the root, your own clone: the branch is its branch, with your remotes and config, and git worktree list there shows the worktree. Perch writes exactly this much in a root: the new branch, git's record of the worktree, a fetch of the one base branch from its remote, on Delete that branch, and when you open a pull request or press Push, a push of the branch and the upstream it then tracks. The fetch uses your own credentials and never Perch's token, and cannot prompt: a key that wants a passphrase fails it, and the cut goes ahead from what the clone had, with a notice saying how old that is. A GitHub repository with no root is cut in Perch's own clone, as Start work on an issue or a pull request is. Start work on a worktree in a local repository cuts in that repository.

Start work from an item

Start Work is on the Worktree row of an item's details, behind the list button in the bar: a button on an item with no worktree, and a row of the worktree's menu on one that has a worktree. It is also in an item row's menu and in the menu of a notification about a pull request or an issue. It cuts a new branch from the item into a worktree of your own and opens it:

  • From an issue, perch/issue-<n> from the default branch.
  • From a pull request, anyone's and from any fork, perch/pr-<n>-work from the head Code shows: the pull request's worktree when it has one, commits not pushed yet and all, else its head on GitHub. The branch is diffed against the pull request's base, so it shows the whole change, and a pull request opened from it takes it over.
  • From a worktree, a new branch from its head, named for it with -2.

An issue or a pull request leaves a prompt to work on it in the new worktree's composer, and a second press opens the worktree the first made. The new worktree is listed under In Perch on the item it came from. A pull request opened from it says Closes #<n>, so merging it closes the issue or the pull request it came from. A merged pull request, and anything archived, has no Start work.

From a notification, Start work cuts from the item Perch has for its pull request or issue, and makes that item first if there is none. It is greyed once Perch has seen the pull request merged or the issue closed. A pull request whose worktree was removed has to be opened first, which restores it. Other kinds of notification have no Start work.

Keeping work safe

A worktree made for work can hold the only copy of it.

  • Delete asks again, naming the count, when the branch has commits no other branch, tag, remote-tracking branch or ref of Perch's holds. A branch pushed from Perch's own clone is not seen as pushed until a pull request brings its head back.
  • Archive of a worktree asks first when the directory holds files git ignores, such as a .env, and names them: archiving removes the directory, and git keeps no copy of those. The branch and its commits stay. Worktrees with no pull request are never archived for age; pull request checkouts still are, after 14 days unopened.
  • A pull request's worktree follows its head when the head moves only if the commit on disk is one the pull request had. A commit you made there and have not pushed keeps the worktree where it is, reported stale, as uncommitted changes do.
  • A worktree of your own is never moved to its pull request's head. When the two are at different commits, the Branch row and the item's bylines say how: 3 unpushed, 2 behind PR, both, or PR head not fetched when the pull request's head isn't in the repository. Perch counts this in the worktree's own repository at each scan and open and fetches nothing to do it. Submit review and Merge are unavailable while the heads differ, since what is on screen isn't what GitHub would review or merge.
  • Update branch, on the Branch row and in place of Merge, shows when the pull request's head isn't fetched or the worktree is only behind it. It fetches the pull request's branch, with your git credentials in one of your clones and Perch's token in its own, and fast-forwards the worktree to its head. A worktree with unpushed commits of its own isn't moved; the fetch only lets the row count both sides. Uncommitted changes to files the pull request changes stop the update.
