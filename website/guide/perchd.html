perchd and engine lifecycle

How one engine locks a Perch home, how headless perchd serves and bridges over SSH, and how the app manages remote builds.

On this page
  • One engine to a Perch home
  • Headless perchd commands
  • The app's own engine
  • When the engine is another build

One engine to a Perch home

Everything below the window, the GitHub client, the cache, the checkouts, the language servers and the agents, is Perch's engine. Whatever runs it, the app or perchd, holds an exclusive lock on $PERCH_HOME/engine.lock while it runs and writes its process id there. A second engine on the same home refuses to start and names the process that has it: the app opens its window and says "Perch could not start its engine: another Perch engine (process …) is running on …", and nothing runs behind it. The lock goes with the process however it ends. On a file system that has no locks, some network ones, the engine runs anyway, warns in the log, and nothing stops a second one. The commands that only read the cache, perch context, perch --items, --agents, --timeline, --scope and --scan, need no lock and run beside an engine.

Headless perchd commands

perchd runs the engine with no window, on a machine the Mac reaches over ssh. It is built from the same crates as the app, without a UI toolkit, so it needs no GTK. It is built for Linux and for a Mac, on x86_64 and arm64, as perchd-linux-<arch>.tar.gz and perchd-macos-<arch>.tar.gz. Linux's is built against musl and linked statically, so it runs on any Linux of its architecture, Alpine included, whatever its libc. Every app has all four built into it and brings the one a host needs to it (see The app's own engine), so nothing is installed on a host first. Releases publish them too, with the SHA-256 of every asset in the release's SHA256SUMS: to run one by hand, put it in ~/.local/bin.

  • perchd serve runs the engine and listens on $PERCH_HOME/run/perchd.sock (the directory owner-only, the socket mode 0600). It keeps polling, sweeping and running agents with no client connected. With --exit-after-idle <seconds> it stops by itself once it has had no client connected and no agent run queued or under way for that long: how a bridge starts one (below). Run by hand with no flag, it stays until it is stopped. SIGTERM, SIGINT or SIGHUP stops it as quitting the app does: running agents are stopped and recorded Interrupted, the socket is removed and the home let go. A bridge of another build asking it to stop over the socket stops it the same way. A second SIGTERM or SIGINT while it stops ends it at once; another SIGHUP does not, as a dropped ssh session sends two. It logs to stderr, in colour only on a terminal, and to $PERCH_HOME/logs, never to stdout. With another engine on the home it exits 75. It does not start on a perch.db a newer Perch has migrated, which it would otherwise run without, its runs unrecorded. When it can't start, it writes why to $PERCH_HOME/run/serve-failed (mode 0600) as well as to its log, and removes the file when it next starts.
  • The engine never keeps the ssh session's SSH_AUTH_SOCK, SSH_CONNECTION, SSH_CLIENT or SSH_TTY, whether a bridge started it or it was run by hand in a login: it outlives the session, and every agent it starts would get them. git over ssh on the host uses the host's own keys. An engine run by hand outside an ssh session, from a desktop login on the host say, keeps SSH_AUTH_SOCK, which is then the host's own agent.
  • perchd bridge joins its stdin and stdout to the socket, byte for byte, until either side closes. It is what the app has ssh run. With no engine answering it starts perchd serve --exit-after-idle 900 in a session of its own, so the engine outlives the ssh connection, and waits up to 10 seconds for it. That engine stops 15 minutes after its last client has gone and its last run has ended (see What runs where); PERCH_IDLE_EXIT_SECS in the host's login environment sets another wait. An engine that failed to start for a reason it left in serve-failed is not waited for: the bridge says that reason. When something holds the home's lock without listening, an engine still stopping or the Perch app running on the host, it names that process. It writes nothing but the engine's messages to stdout. A bridge the app put there, one run from $PERCH_HOME/bin/perchd-<build>, marks its own file as used now, and removes the other perchd-* there that nothing has used in a week, and the temporary files of uploads that stopped over an hour ago. When a build was last used is its file's modification time.
  • perchd bridge --replace makes way for its own build. An engine of another build is asked over the socket to stop, and stops as SIGTERM stops it. The bridge waits up to a minute for its socket to stop answering and the home's lock to be free, then starts its own engine and carries on as a bridge; if another bridge has started an engine there meanwhile, it joins that one. An engine of its own build is joined as it is. Builds are the same or they are not: which version is the later is never asked. --replace-if-idle does the same only when the engine has no runs and no clients; otherwise it writes perch-busy: <version> <runs> <clients> to stderr and exits 98, leaving the engine running. Nothing is ever signalled or killed by its pid. The Perch app running on the host holds the home with no socket, and can't be replaced: quit it there. A build is the <build> of the perchd-<build> it runs as, the first 12 hex digits of the binary's SHA-256, or its version when no app put it there.
  • perchd status connects without starting anything and prints whether an engine is running, its version, protocol and build, its Perch home, how many other clients are connected and how many agent runs are queued or under way. It exits 0 when one answers and 3 when none does.
  • perchd context prints what Perch knows about the item a worktree on the host is for, from the host's database, for an agent working there. It takes what perch context takes (see Context for agents outside Perch). The engine, as it starts, links $PERCH_HOME/bin/perchd to its own build, so ~/.perch/bin/perchd context reads the database with the build that has it; a file there that is not a link is left alone.
  • perchd --version prints the version and the wire protocol, as perchd 0.9.0 (protocol 6).

A socket file left by an engine that was killed is removed when the next one starts, once nothing answers on it.

A bridge is the only thing that starts an engine on a host. After the host boots, after an engine crashes, or once one has stopped for having nothing to do, nothing runs there until the app next connects. Stopping the engine while the app is connected does not keep it stopped: the app reconnects and its bridge starts another. Quit the app, or set it to This Mac, first. On Linux the engine needs logind's KillUserProcesses=no, the default on most distributions; with yes, it is killed when the ssh session that started it ends, its runs with it, unless the user is in KillExcludeUsers. A user KillOnlyUsers names is killed whatever KillUserProcesses says. The engine checks this (see What the app checks).

The app says it is still there every 15 seconds it has nothing else to send, and the engine hangs up on a client it has heard nothing from in a minute: a Mac asleep, or off the network, would otherwise hold its windows' open items and language servers until TCP gave up on it, hours later. A client that connects and never says hello is hung up on after the same minute. The Mac's windows reconnect when it wakes. While the app is connected to a host it opts out of App Nap, which could hold its keepalives back while it is hidden.

The app's own engine

With no [remote] command, the app runs its own perchd on the host. It carries one for each system and processor inside its own binary, put there when the app was built (see How an app gets its engines): nothing is downloaded, and nothing is read from beside the app. The host keeps the one it was sent as ${PERCH_HOME:-~/.perch}/bin/perchd-<build>, where <build> is the first 12 hex digits of the binary's SHA-256, 1a2b3c4d5e6f. So the same engine is never sent twice, whichever app has it, and a different one never takes its name. There are no versions in it: two apps carry the same engine or they do not.

  • The host's login shell runs a short sh script, which is given the build of each engine the app carries. It starts the bridge of the one for what the host is, which starts the engine if none is running and joins it if one is. With that build not there, it writes perch-install: <uname -s> <uname -m> to stderr and exits 97.
  • On that line the app sends the engine and connects again at once, outside the waits between tries. The strip at the foot of the window says "Sending perchd 0.9.0 to <host>…" meanwhile, with how far it has got under it. Linux and macOS, on x86_64 or on aarch64 or arm64, have a perchd; any other host says what it is and to put perchd there by hand and set [remote] command.
  • A second ssh, with the same options, sends the binary to a script on the host that writes it to a temporary file in bin (the directory and the file owner-only), takes its SHA-256, and puts it in place only when that is the one the app said: an upload cut short, or changed on the way, is never run. The host needs sha256sum, shasum or openssl for it. A build that is already there is left as it is, so two apps sending the same one at once do not put a file under one another. The temporary file is removed when anything fails, the ssh session ending under it included.
  • A send that goes through, after which the host still says it has no perchd, stops the tries and says so rather than sending again: most often a login shell there that sets another PERCH_HOME. An upload that fails is tried again with the next try.
  • An app with no perchd for the host, and no source to build one from, says so and stops the tries.

How an app gets its engines

Building the app builds its engines: crates/perch-app/build.rs builds perchd for Linux and macOS, on x86_64 and arm64, with the app's own profile, gzips each into the app's binary and records its SHA-256, so the app can name its builds without unpacking them. The app itself is built for the machine it is built on only. This is so of every build, cargo run as much as a release's.

  • A Linux perchd is built against musl through cargo zigbuild, zig being the C compiler and linker for it from any machine: it needs zig and cargo-zigbuild (brew install zig, cargo install cargo-zigbuild). On Linux with neither, this machine's own processor's is built with musl-gcc when that is installed.
  • A macOS perchd is built by the Rust toolchain on a Mac, for either processor. Anywhere else it needs Apple's SDK: it is built through zig when SDKROOT names one, and is left out otherwise.
  • rust-toolchain.toml names the four targets, so rustup installs them.
  • One whose tools are missing is left out, with a warning from the build that says what to install, and the app carries the rest. One that does not compile fails the app's build.
  • They are built in engines under cargo's target directory, apart from the app, and built again when anything perchd is made from changes.
  • With PERCH_ENGINES set to a directory, by its whole path, nothing is built: the four perchd-<linux|macos>-<x86_64|arm64>.tar.gz there are taken, and one missing fails the build. A release is built so, each engine on a runner of its own system. With PERCH_ENGINES=none the app carries none and nothing is built, for a quick build of the app alone. Under clippy and rust-analyzer nothing is built either.

For a host the app carries no engine for, an app whose source is still where it was built builds perchd from it then: on the host's perch-install line it builds for what the host is, and uploads it as a carried one is, under its own hash. The strip says "Sending perchd 0.9.0 (built from source) to <host>…" through both. A Linux host's is built with cargo zigbuild against musl, and a Mac's with cargo build from a Mac; when a tool is missing the strip says which, with the command. Each launch builds again, which cargo makes quick when nothing changed, and asks the host whether it has that build before uploading it.

[remote] command, when set, is run instead, and nothing is sent.

Each bridge the app put there removes the builds beside it that nothing has used in a week (see perchd). A build an app still connects with is used each time it does, so two apps of different builds each keep theirs on the host.

When the engine is another build

The app on the Mac looks for its own updates, as it does with no host: Check for Updates… and Restart to update work while disconnected, and never go to the host's engine. It asks GitHub with no token, since the host has the token and the repository is public.

An updated app carries another engine, so its next connection sends the new perchd, which goes beside the old. The engine already running on the host may be the old build still, though one nobody has used for 15 minutes has stopped by then (see What runs where) and the new one simply starts. One still running is another build than the app's, as is a dev build rebuilt, or another Mac's app of another version. Builds are never ordered, only told apart, and the app wants its own:

  • No runs and no other client connected: the app hangs up and connects again with perchd bridge --replace-if-idle, which stops that engine and starts the app's. The strip says "Restarting the engine on <host> to run perchd <build>…" meanwhile, and the log says so. It does this once a connection: an engine still another build after it is left running.
  • Busy, with runs or another Mac connected: the app leaves it running. When it speaks the app's protocol, the app connects to it as usual and the strip says "<host>'s engine is perchd 0.8.0 (1a2b3c4d5e6f); restart it to run this app's, perchd 0.9.0 (2 agent runs would be stopped)", with a Restart button. When it doesn't, the strip says the same without a connection, with Restart and Reconnect. Restart connects with perchd bridge --replace, which stops the engine whatever it is doing: its runs are recorded Interrupted, as when the app quits, and other Macs connected to it reconnect to the new one. An engine that comes into use between the app's look and its --replace-if-idle is left running, and the strip offers the restart; the app connects to it when it speaks the app's protocol. The counts the strip names are from when the app connected, and are not brought up to date while it stays connected.
  • Two Macs with different builds, at the same host, take turns: the first to connect has its engine, the second joins it while it speaks the second's protocol, and each replaces the other's only when the other's has nothing running and nobody connected. An app older than the engine it replaces can find perch.db moved on by the newer one, which its own perchd does not start on: the strip says so, and to update Perch on that Mac.

With [remote] command set none of this happens: the app uses whatever engine the command reaches.

The app's first message, and the engine's answer, are frozen as of protocol 5: later versions only add fields that may be left out. So an engine of any later protocol still says who it is when it refuses the app, and still hears a request to stop. An engine from before protocol 5 says nothing of itself and can't be asked to stop; the strip says to stop its perchd serve on the host and reconnect.

perch --connect [host] does what the app does to connect, with no window: it sends perchd if the host needs it, replaces an engine of another build with nothing running, prints the engine's version, protocol, build, host name, home and data folder, how many other clients it has and how many runs, and exits 0. An engine of another build left running for its runs is said after that, and then the host's checks, a line each, with the command to run under each that failed (see What the app checks). It waits up to 30 seconds for them, as an engine that has just started looks after it has found the agents. It reads [remote] from the Mac's config.toml, and [remote] host when no host is given. On failure it says why and exits 1.
