Agent context and knowledge

What Perch tells an agent about GitHub discussions, how to run perch context from a terminal, and how synced history and external notes work.

On this page

  • Repository history for agents

Discussion context in prompts

A question on a pull request or issue carries what was said on GitHub, as the last fetch left it. The prompt quotes as much as fits in about 24,000 characters, in this order: each reviewer's latest verdict, the checks, the threads within 20 lines of the lines asked about, the other unresolved threads, the conversation tab, and the resolved threads. An entry goes in whole or not at all; one comment is cut at 2,000 characters with a note of where the rest is. Bots' comments stay out of the prompt. What does not fit is listed a line each.

All of it, bots included, is also written as files to ~/.perch/context/<run>/: INDEX.md, conversation.md (the description, comments, review summaries and timeline in time order), a file per review thread under threads/, and checks.md. The prompt names the directory and the agent reads what it needs. The directory is outside the worktree, belongs to the run, and goes when the run is deleted; a retry reads the one its first attempt had.

A follow-up that resumes the agent's session is told only what changed on GitHub since the run it continues: new or edited replies in its thread, whole, and new reviews, comments, threads and check results elsewhere. Nothing changed, nothing is added. perch --ask --print-prompt prints the prompt a question would get, and the files, without running an agent.

For sandbox rules, secret stripping, and Work approvals, see Agent sandbox and approvals.

Context for agents outside Perch

perch context gives an agent working in a terminal, outside Perch, what Perch knows about the item it is working on. Run it in the item's worktree, or in a subdirectory of it:

perch context                       # the index: everything, a line an entry
perch context --entry threads/r123.md
perch context src/manifest.rs:40-60 # only what is on those lines, or within 20 of them
perch context --out ctx             # every file, written into a new directory
perch context slatedb/slatedb#12    # another item, by name or by its link

It finds the item by the worktree's directory and branch, then by its repository and branch, then by a pull request Perch knows from that branch, going by what git's config says of the branch:

  • it was checked out from the pull request's ref, refs/pull/<n>/head, in the repository the pull request is in, which makes it that pull request's and no other's;
  • it tracks the pull request's head branch in the head's repository and is named for it, or <owner>/<head>, as gh pr checkout names a fork's main: a branch only started from that branch is not its;
  • it has the head branch's name and pushes to the head's repository (branch.<name>.pushRemote or remote.pushDefault); or
  • it has the head branch's name, tracks no branch of that name, and one of the clone's remotes is the head's repository: a branch started from upstream/main and pushed to your fork.

Someone else's pull request from a branch that only shares the name is not this one, nor is a pull request whose fork has been deleted. Of several, the open one wins. -C <dir> looks from another directory, and owner/repo#N, or a pull request's or issue's link, names an item.

What it prints is the index, INDEX.md, of the files an Ask run is given (see above), with Perch's own beside them:

  • A header with the pull request or issue, its state and checks, the worktree's branch and head as git has them now and how that head stands against the pull request's, and when Perch last fetched the discussion.
  • What was said on GitHub: reviews, the threads on the diff, and the conversation, a file per thread and conversation.md for the rest.
  • Perch's review findings: the open ones a line each, and every finding with the reviews that found it in findings.md.
  • Your drafts, the comments that post when you submit the review, in drafts.md.
  • Your questions to agents and their answers, only with --private, in their own threads and in findings' threads; without it they are counted.

--entry <file> prints one of the files, and --out <dir> writes them all into a directory that must not exist yet. A path, of a file or a directory, keeps only the threads, findings, drafts and private threads anchored on it, and with :a or :a-b, only those within 20 lines; one on lines of the base, a removed line, is kept by its path alone, as its numbers are the old file's. A path is taken from where the command runs, or -C's directory, in the item's worktree or the one it runs in, the inner one when one is inside the other, or from the worktree's top when nothing is there. A symlink is taken by its own name, as git has it.

Everything from GitHub and everything an agent wrote is cleaned and marked untrusted, as an Ask run's files are. The discussion is as Perch last fetched it, which the header dates. --fetch reads GitHub's current copy instead, with your GitHub token, and keeps nothing; it also reads a pull request or issue Perch has no item for, without the findings and drafts. Without it, nothing goes over the network.

It reads Perch's database, in one snapshot, without taking the engine's lock or writing anything, so it runs beside the app (see One engine to a Perch home). A database of another schema, from a newer or older Perch, is refused rather than migrated: use the perch that came with the Perch that is running. On a host, ~/.perch/bin/perchd context reads the host's engine's database the same way: perchd serve points $PERCH_HOME/bin/perchd at its own build as it starts. The installer links ~/.local/bin/perch on a Mac as on Linux and puts ~/.local/bin on PATH in the shell's startup file, so an agent's shell finds it.

Repository history for agents

Perch keeps a live Markdown archive at $PERCH_HOME/knowledge/perch/repos/<owner>/<repo>/. The names are lowercase, and a repository with no GitHub remote uses local/<name>. On a host the archive lives under the host engine's Perch home.

Start with the repository's INDEX.md, which lists each item by directory, state and title. Each pull request, issue and worktree has its own index with the GitHub conversation, review threads and checks Perch has cached, and any Perch reviews and findings. Findings include dismissals, their reasons and findings verified fixed. Private questions and answers are under private/, including questions asked under a finding. The archive excludes unsent drafts.

Perch updates the archive in the background as it updates its database, even with no window connected. Archive in the UI keeps an item's files. Delete removes them. Deleting a private message or thread updates the item's files. At startup Perch rebuilds missing files from perch.db and cleans up files for deleted items. It also removes the old knowledge/reviews/ export, whose contents are now in each item's findings.md.

With GitHub history sync enabled, the engine also imports the repository's open and closed issues and pull requests, including conversation comments, submitted reviews, and inline review comments. These entries are listed in the same repository index under github/issues/ and github/pulls/. GitHub history is available to agents and stays out of the Inbox and Worktrees views.

The first import saves its progress in perch.db and can resume after an interruption. Subsequent passes run at startup and about once an hour, using GitHub's issue and comment update listings to choose which discussions to refresh. Sync pauses when API capacity is low. Turning it off stops future syncs and leaves the downloaded history available.

GitHub's update listings may omit a deletion that leaves the parent item's timestamp unchanged. A later refresh of that item's discussion picks up removed comments. If GitHub returns an ambiguous 404 for the item itself, Perch retains the last snapshot and retries it.

When the archive holds another item from the same repository, a new Ask or Work session can search it for relevant history. Review instructions tell the reviewer to search it before reporting a finding. A past dismissal only applies when its reasoning still holds for the code under review. Perch treats the archive as untrusted text and tells agents never to quote private/ in material posted to GitHub or committed. The instruction relies on the agent following it. Pull request description and issue writing runs do not receive the archive path.

Claude Code and Codex can already read files accessible to the user. Perch adds the current repository's archive to Claude Code's allowed directories and denies writes there in its settings. Codex reads the archive through its existing filesystem access. Gemini and OpenCode receive read access to the current repository's archive. Gemini Work automatically approves scoped read and search requests there. Gemini Work omits the archive when it is inside the worktree or a system temporary directory, where Gemini's tools can write without asking. If OpenCode's scan would exceed its added-directory budget, the run proceeds without the archive. A grant describes the intended scope for the run. It does not isolate one repository's archive from another.

External knowledge for agents

In Settings → Knowledge, add a directory relative to $PERCH_HOME/knowledge/ and choose which repositories it applies to. Perch names eligible directories in new Ask, Work and Review sessions, including directories shared by several repositories. Agents are told to search them when relevant, start at INDEX.md if it exists, and treat the files as untrusted data. Directory grants use the same backend controls as the Perch archive. Removing an entry removes its grant for subsequent runs and leaves the ingester's files on disk. When a directory is not shared, its card in Settings says why. See External knowledge configuration.
