The inbox

Polling and screen stability

Perch builds its inbox from GitHub's REST notifications list. It preserves the API's order and unread state, and caches the latest response locally so the sidebar can paint immediately. Perch requests all=true so read threads remain visible alongside unread ones. If the list cannot be written to the local database, the sidebar still shows it, leaving out what is Done or snoozed as the marks on disk say.

Polling runs in the background, respects GitHub's X-Poll-Interval, and paginates the full response. Perch performs an unconditional reconciliation at startup and on the first scheduled poll after 15 minutes. Polls between reconciliations ask for the first page only if its ETag has changed, and read the whole list again when it has. New activity always changes the first page. A thread past the first fifty does not when it is read or marked Done on github.com, or when only its time moves (your own comment or review, a label), and the reconciliation picks that up. Without a token, each poll looks for one again, so a gh auth login after launch is picked up.

A poll never moves what is on screen. When it would add, remove, or reorder the rows the sidebar shows, the rows stay as they are and a pill over the list says how many are new, with Refresh to show them. Changes inside a row, such as read state, go straight in, and anything you do in the sidebar shows the latest list. When a notification arrives about the open pull request or issue, a pill over the pane offers to fetch it. A CI notification for the open pull request updates its checks directly, as long as the head on screen is still GitHub's.

Read state, Done, and snoozing

  • Viewing a pull request or an issue marks its GitHub thread read, from whichever row it was opened: the notification's, or the item's in All or Authored. Read threads remain in the inbox. While the thread is unread, the item's row is bold with the unread dot, as the notification's row is. GitHub's list can go on reporting a thread unread for a while after it has taken the request, so a read made in Perch holds for that revision of the thread until newer activity arrives or it is marked unread; a thread marked unread on github.com for the same revision is not seen.
  • Opening an unread notification, from its row or from the item's in Worktrees or Browse, goes to what it is about: Conversation scrolls to the newest comment, review, reply or event no later than the notification, and the card flashes. A resolved thread with the reply is opened. The cached discussion paints first, so the page waits up to a few seconds for GitHub's answer to bring the new activity, then settles for the newest card it has. Scrolling first leaves the page where it is, and a read notification opens where the page was left.
  • Mark Unread, on the notification's row or the item's, puts an unread reminder on the thread in Perch. Viewing it in Perch clears the reminder, and newer activity GitHub reports unread takes its place. A later update GitHub reports read leaves it: your own comment or review moves the thread too, and so does activity you have already read on github.com. GitHub's public API has no mark-unread operation, so this does not change github.com.
  • Done marks the thread done on GitHub and remembers that update in Perch, so GitHub's all=true history cannot put it back. Newer unread activity clears the local mark and lets the thread return. A later update GitHub reports read does not: your own comment, review or merge moves the thread too, and so does activity you have already read on github.com. Done is for the update the row shows. Perch reads the thread from GitHub just before marking it, one extra request per thread, and a thread with newer unread activity is not marked Done. One the pill over the list was holding back stays, with what arrived, and so does the pane showing it; one that arrived since the last poll comes back behind the pill. A notice says so either way. A comment that lands between that read and the Done still goes with it: GitHub's Done takes whatever the thread holds.
  • Unsubscribe ignores future activity on the thread, marks its current notification done, and remembers it the same way. Whatever has arrived on the thread goes with it.
  • A thread whose pull request you merged or closed, or whose issue you closed, with nothing on it since, is marked Done on its own, on GitHub too. A merge or close by anyone else stays in the inbox, read or not, so you see it. Perch waits a minute after the close first: GitHub sends the close's own notification some twenty seconds late, and a Done before it would see the thread come back. A comment more than a minute after the close keeps the thread, or returns it; one inside that minute is taken for the close's own notification. The thread is read first here too, and one with newer unread activity waits for the poll that brings it.
  • View › Done, in the Inbox's filter menu, lists the threads marked Done in Perch that GitHub still lists. Move to Inbox, on the row or its menu, drops the local mark and puts the thread back. GitHub's public API has no way to undo Done, so github.com keeps it under Done. A closed thread you move back to the inbox stays; only a later merge or close, with nothing after it, marks it Done again.
  • Snooze, the clock on a row or the Snooze submenu in its menu, hides the thread until later today (6 PM), tomorrow, later this week, this weekend or next week (8 AM), as Gmail offers them. It comes back sooner if newer activity arrives that GitHub reports unread. When the time comes it returns to its place in the inbox, as read or unread as it was snoozed. View › Snoozed lists the snoozed threads with when each returns, and Move to Inbox ends a snooze early. GitHub has no snooze, so the mark lives only in Perch and github.com still lists the thread.
  • State › Merged or Closed narrows the inbox to threads whose pull request has been merged or closed, or whose issue has been closed. A thread whose subject Perch has not looked up yet counts as open, and so do kinds with no state, such as releases and CI runs.
  • Mark N Done, at the foot of the filter menu, marks every thread the inbox is showing Done, one GitHub request after another, each read first, so a thread with new unread activity is left in the inbox, and reports any failures in a single notice. Filtering to State › Merged or Closed first clears the finished pull requests in one go. On View › Done and View › Snoozed the same item reads Move N to Inbox.
  • Pull requests and issues open inside Perch. Other notification types remain first-class inbox rows and open on GitHub.

The sidebar's filter menus

Each tab has one filter menu, laid out the same way: View, then what the list is narrowed to, then Sort By, then display settings and actions. A section is left out only where it cannot apply. The button lights up while the tab's list differs from its defaults, and the search box names the view it searches.

  • Inbox: View (Inbox, Snoozed, Done; then Review requested, Yours, Assigned, Mentioned, All, from GitHub's reason, Yours also taking what you opened), Repository, State, Sort By (Newest or Oldest first), Unread Only, Mark N Done.
  • Worktrees: View (Worktrees, or Recent: everything opened, worktree or not), Repository, State, Sort By (Last activity, Last opened, Created; each view keeps its own), Unread Only.
  • Browse: View (Review requested, Yours, Assigned, Mentioned, All), Repository, State, Sort By (Last activity or Created, sorted by GitHub's search). Repository offers every repository on GitHub that config, Worktrees or Inbox knows of. All searches the repository picked, or every declared repository on GitHub.

Repository is shared by all three tabs. State is Any, Open, or Merged or Closed everywhere; it defaults to Any on Inbox and Worktrees and to Open on Browse.

GitHub's public REST notification payload does not expose whether a thread is currently in the web Inbox or Done, and all=true can include Done history. Perch can therefore keep its own Done actions stable, but cannot reliably mirror Done or Restore actions performed on github.com.

These actions affect only the notification or its local reminder. They do not archive or delete a Perch item, worktree, or local conversation.

Finished runs on your own work

A worktree with no pull request has no one on GitHub to notify you, so Perch does. When an Ask or Work run, or a worktree review, ends on it, the item gets a row in the inbox: its glyph and title as Worktrees draws them, then the repository, the branch, and what happened: Claude · Work · 3 files, Codex · Ask, Review · 2 findings, in the failure colour when it failed. A run you stopped or cancelled, or that ended because Perch quit, doesn't count, and neither does one on the item open in a window that's in front: you watched it. A Claude Code or Codex session you started yourself, outside Perch, isn't seen.

The item has one row, for the last run that ended there. It fits in among GitHub's rows by time, and waits behind the pill as a poll does. It is unread until you open the item, from any row, and the item's row in Worktrees is bold with the dot until then too. Opening it opens the item. Mark Unread puts the dot back. Done puts it away until the next run ends there; it never archives the item or touches its worktree. Local rows are under View › Inbox with Yours or All, not under GitHub's own reasons, and have no Snooze.

Once the item has a pull request, GitHub's notifications are its signal: its row goes, and a run that ends there makes none, only the notice a run leaves as it finishes.

Perch fetches a pull request or issue when you open a notification or open the item by repository and number. For agents, you can also enable GitHub history sync per repository.
